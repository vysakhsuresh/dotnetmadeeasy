Strings and Text

How C# represents, manipulates, and optimises text — from simple messages to massive documents.

Every app you'll ever build deals with text — user names, error messages, JSON responses, log files, or the content of a blog post. In C#, text is represented by the string type, and understanding how it works is one of the most important skills you'll learn.

But strings in C# are not just arrays of characters. They have superpowers — and some surprising behaviour that can trip you up if you're not careful.

Let's explore what strings are, how they work under the hood, and how to use them effectively in .NET 10 with C# 14.

What Is It?

The Simple Explanation

A string is a sequence of characters that represents text. In C#, you write strings inside double quotes: "Hello, World!".

The Technical Definition

In C#, string (alias for System.String) is an immutable reference type that represents a sequence of UTF‑16 code units. Immutable means once a string is created, it cannot be changed — every operation that "modifies" a string actually creates a new string.

Strings are null‑terminated internally and store their length and character data in a contiguous block of memory. .NET 10 (with C# 14) continues to evolve string handling with performance improvements like Span<char>, Utf8String, and enhanced interpolation.

string → System.String → UTF‑16 text → Immutable
A string is a sequence of UTF‑16 characters, stored in memory, that never changes once created.

Why Does It Exist?

The Problem

Text is everywhere, but representing it in a computer is surprisingly complex. Early languages used simple arrays of bytes (ASCII) that couldn't handle accents, emojis, or non‑English scripts. Developers had to manually manage memory, track lengths, and handle encoding — leading to countless bugs and security vulnerabilities.

The Solution

C# and .NET provide a first‑class string type that abstracts away all the low‑level details. You get:

  • Unicode support — text in any language, including emojis
  • Automatic memory management — the runtime handles allocation and cleanup
  • Rich manipulation methods — search, split, join, format, and more
  • Performance optimisations — string interning, Span, and Utf8String in modern .NET
🧠 The key insight

Strings in .NET are not just character arrays — they are a high‑level abstraction that gives you safety and productivity, while the runtime handles encoding, memory, and performance under the hood.

How It Works

Let's break down the key mechanisms that make C# strings work:

1. Immutability

Once created, a string's content never changes. When you call ToUpper(), Replace(), or concatenate with +, you get a brand new string — the original remains untouched.

// Example: immutability in action
string s1 = "Hello";
string s2 = s1.ToUpper();   // "HELLO" — new string
string s3 = s1 + " World";  // "Hello World" — new string
// s1 is still "Hello" — unchanged

2. String Interning

To save memory, the CLR maintains an intern pool. When you create a string literal ("Hello"), the compiler checks the pool — if the same string already exists, it reuses the reference.

// Interning example
string a = "Hello";
string b = "Hello";
// a and b reference the SAME object in memory
bool same = object.ReferenceEquals(a, b); // true

3. UTF‑16 Encoding

Internally, strings are stored as a sequence of UTF‑16 code units (2 bytes each). Most characters fit in one code unit, but some (like emojis) require two (surrogate pairs).

4. Performance: Span<char> and Utf8String

In .NET 10 / C# 14, you can work with strings more efficiently:

  • Span<char> — slice a string without allocating new memory
  • Utf8String — a UTF‑8 encoded string for better performance in web/API scenarios

Simple Example

Let's start with the most common string operations:

// Basic string creation and manipulation
string name = "Ada";
string greeting = $"Hello, {name}!";   // string interpolation
Console.WriteLine(greeting);           // Hello, Ada!

// Common methods
string upper = name.ToUpper();         // "ADA"
string lower = name.ToLower();         // "ada"
bool contains = name.Contains("d");    // true
int length = name.Length;              // 3

// C# 14 / .NET 10: Count occurrences (new overloads)
int count = name.Count(c => c == 'a'); // 2

What's happening?

  • "Ada" is a string literal — interned and stored in the pool.
  • Interpolation ($"...") creates a new string by combining the template and the variable.
  • ToUpper(), ToLower(), Contains() all return new strings or booleans — the original name is unchanged.
  • Count() is a LINQ method that counts matching characters (requires using System.Linq;).

Real‑World Example

Imagine you're building an e‑commerce API that processes customer orders. You need to:

  • Sanitise user input (remove extra spaces)
  • Format order summaries
  • Generate JSON responses efficiently
// Real-world: order processing with strings
public class OrderService
{
    public string BuildOrderSummary(string customerName, decimal total, string[] items)
    {
        // 1. Sanitise input
        string cleanName = customerName.Trim();

        // 2. Format using interpolation (new in C# 14: better performance)
        string summary = $"""
            Order for {cleanName}
            Total: {total:C}
            Items:
            {string.Join("\n  - ", items)}
            """;

        // 3. Use Span for efficient slicing (no allocation)
        ReadOnlySpan<char> firstItem = items.Length > 0
            ? items[0].AsSpan()
            : ReadOnlySpan<char>.Empty;

        // 4. Return the summary
        return summary;
    }
}

What's happening?

  • Trim() removes leading/trailing whitespace — a new string is returned.
  • Raw string literals (""") from C# 11+ make multi‑line text clean and readable.
  • string.Join() efficiently combines an array into a single string.
  • AsSpan() creates a view of the string without copying — ideal for reading parts without allocation.

Analogy

📜 Strings are like books

Think of a string as a book.

  • The text is the content of the book — once printed, you can't change the words (immutability).
  • ToUpper() is like buying a new edition with all capital letters — the original book stays as it was.
  • Substring() is like photocopying a chapter — you get a new copy of just that part.
  • StringBuilder is like a whiteboard — you can erase and rewrite without creating a new board each time.
  • String interning is like a library that keeps one copy of each book title — if two people ask for the same book, they get the same physical copy.

The book analogy works because it captures immutability, sharing, and the cost of copying — all central to understanding strings in .NET.

Common Confusion

string vs String vs System.String

🧩 string == String == System.String

string is a C# alias for System.String. They are exactly the same type. Use whichever you prefer — but string is more idiomatic in C# code.

Reference Type vs Value Type

Confusion: "Strings are reference types, but they behave like value types because they're immutable."

Clarification: string is a reference type stored on the heap. However, because it's immutable, you can't accidentally change it through a reference — which makes it feel like a value type. This is a deliberate design choice for safety and simplicity.

Character Count vs Byte Count

Confusion: myString.Length returns the number of UTF‑16 code units, not necessarily the number of Unicode characters. An emoji like "🚀" is two code units (a surrogate pair) but one character.

// Length vs. character count
string rocket = "🚀";
Console.WriteLine(rocket.Length);    // 2 (surrogate pair)
Console.WriteLine(rocket.EnumerateRunes().Count()); // 1 (Unicode scalar)

Common Mistakes

Mistake 1 — Concatenating strings in a loop

❌ Wrong: Using + or += inside a loop creates a new string each iteration — O(n²) performance.

// BAD — O(n²) allocation
string result = "";
for (int i = 0; i < 1000; i++)
{
    result += i.ToString();   // new string each time!
}

✅ Correct: Use StringBuilder for frequent concatenation.

// GOOD — O(n) with StringBuilder
var sb = new StringBuilder();
for (int i = 0; i < 1000; i++)
{
    sb.Append(i);
}
string result = sb.ToString();

Mistake 2 — Using == vs Equals() incorrectly

❌ Wrong: Assuming == compares content for all types. For strings, it does compare content (because it's overloaded), but for object it compares references.

✅ Correct: Use string.Equals(a, b, StringComparison.Ordinal) for explicit, culture‑aware comparison.

Mistake 3 — Ignoring culture when comparing strings

❌ Wrong: "straße".ToUpper() == "STRASSE" — in German, this is true for some cultures but false for others.

✅ Correct: Always specify StringComparison for comparisons. Use StringComparison.Ordinal for internal/technical strings, and StringComparison.CurrentCulture for user‑facing text.

When Should I Use It?

Use strings for:

  • User‑facing text — labels, messages, notifications
  • Data representation — JSON, XML, CSV, logs
  • Identifiers — usernames, product codes, IDs (as strings)
  • Input/output — reading from files, APIs, databases
  • Formatting — dates, numbers, currency (using ToString() and interpolation)

Use alternatives when:

  • Frequent concatenation → StringBuilder
  • Reading without allocation → Span<char> or ReadOnlySpan<char>
  • High‑performance UTF‑8 processing → Utf8String (new in .NET 10)
  • Parsing structured data → use System.Text.Json or System.Xml rather than manual string parsing

Key Takeaway

  • A string is a sequence of UTF‑16 characters — immutable and reference‑based.
  • Immutability means every operation creates a new string; use StringBuilder for repeated changes.
  • String interning reuses literal strings to reduce memory footprint.
  • Use Span<char> for zero‑allocation substring operations.

1. Why are C# strings considered immutable, and what is the practical consequence of this design?

  • A) They cannot be changed, so every operation that appears to modify a string creates a new string object
  • B) They are stored in the stack, making them faster but limited in size
  • C) They can only be assigned once, like a constant
  • D) They are value types, so they are copied on every assignment
Show answer

✅ Correct: A

Why A is correct: Strings are immutable — once created, their content never changes. Methods like ToUpper(), Replace(), and concatenation all create new string instances. The original string remains untouched and can be reused safely.

❌ Why B is incorrect: Strings are reference types stored on the heap, not the stack. They are not limited by stack size.

❌ Why C is incorrect: You can assign a new string to a variable at any time (e.g., s = "new"). Immutability applies to the content of the string object, not the variable reference.

❌ Why D is incorrect: Strings are reference types, not value types. Assignment copies the reference, not the content.

Reinforcement: Immutability makes strings thread‑safe and prevents accidental modification, but it also means you must use StringBuilder when performing many modifications to avoid creating many temporary objects.

2. You're building a logging system that writes 10,000 log entries per second. Each log entry is built by concatenating a timestamp, log level, and message. Which approach is most efficient?

  • A) Using string += to build each log entry
  • B) Using StringBuilder to build each log entry
  • C) Using a List<string> and string.Join() for each entry
  • D) Using string.Format() for each entry
Show answer

✅ Correct: B

Why B is correct: StringBuilder is designed for building strings with multiple appends. It maintains a mutable character buffer and only allocates a final string when ToString() is called. This avoids the O(n²) allocation overhead of repeated concatenation.

❌ Why A is incorrect: string += creates a new string on every operation — for 10,000 entries, that's 10,000 allocations per second, which is extremely inefficient.

❌ Why C is incorrect: Using List<string> + string.Join() still requires storing all parts and then joining — it allocates multiple strings (the parts) before the final result. StringBuilder is more efficient for sequential building.

❌ Why D is incorrect: string.Format() is convenient but still creates a new string per call and has similar overhead to concatenation when used many times.

Reinforcement: In high‑throughput logging, use StringBuilder or consider using a pooled buffer (ArrayPool<char>) for even better performance. In .NET 10, Utf8String could also be relevant if you're writing UTF‑8 logs directly.

  • A) True
  • B) False
  • C) Compiler error
  • D) NullReferenceException

Why A is correct: a == c compares the content of the strings, not references (because == is overloaded for strings). a is "Hello" and c is "HELLO" (since c = b and b = a.ToUpper()). But wait — a.ToUpper() returns "HELLO", so b is "HELLO", and c is "HELLO". So a == c compares "Hello" to "HELLO" — they are not equal. Actually, let me re‑evaluate.

Correction: a is "Hello". b is a.ToUpper() = "HELLO". c = b so c is "HELLO". a == c compares "Hello" to "HELLO" → False. So the correct answer is B.

✅ Correct: B

Why B is correct: a is "Hello" and c is "HELLO". The == operator performs a case‑sensitive ordinal comparison, so they are not equal.

❌ Why A is incorrect: They are not equal — one is "Hello", the other is "HELLO".

❌ Why C is incorrect: The code compiles fine.

❌ Why D is incorrect: No strings are null, so no exception.

Reinforcement: This tests your understanding that ToUpper() returns a new string and that == compares content. It also highlights that string operations are case‑sensitive by default.

4. Which of the following is the best way to efficiently extract a substring without allocating a new string in .NET 10?

  • A) myString.Substring(start, length)
  • B) myString.AsSpan(start, length)
  • C) myString.Remove(start, length)
  • D) myString.Slice(start, length)
Show answer

✅ Correct: B

Why B is correct: AsSpan() returns a ReadOnlySpan<char> that references the existing string data without allocating a new string. This is a zero‑copy operation and is the recommended approach for high‑performance scenarios in .NET 10.

❌ Why A is incorrect: Substring() allocates a new string, which is what we want to avoid when efficiency is critical.

❌ Why C is incorrect: Remove() also creates a new string and is used for deletion, not extraction.

❌ Why D is incorrect: Slice() is a method on Span<T>, not directly on string. The correct way to get a slice from a string is via AsSpan().

Reinforcement: Span<T> is a game‑changer for string processing in .NET. It allows you to work with parts of a string without copying, making your code faster and reducing GC pressure. Use it when you need to read, not modify, substrings.

5. You're comparing two strings for equality in a case‑insensitive manner. Which approach is both correct and explicitly specifies the comparison rules?

  • A) a.ToUpper() == b.ToUpper()
  • B) string.Equals(a, b, StringComparison.OrdinalIgnoreCase)
  • C) a.Equals(b)
  • D) a == b
Show answer

✅ Correct: B

Why B is correct: string.Equals(a, b, StringComparison.OrdinalIgnoreCase) explicitly specifies a case‑insensitive ordinal comparison. It's the most correct and readable way to compare strings with explicit rules, and it avoids creating intermediate strings (unlike ToUpper()).

❌ Why A is incorrect: Using ToUpper() creates two new strings and is less efficient. It also has culture‑specific behaviour that may not be desired for technical comparisons.

❌ Why C is incorrect: Equals(b) performs a case‑sensitive ordinal comparison by default, not case‑insensitive.

❌ Why D is incorrect: == is also case‑sensitive by default.

Reinforcement: In .NET, always specify StringComparison for clarity. Use Ordinal or OrdinalIgnoreCase for internal/technical strings, and CurrentCulture for user‑facing text. This prevents subtle bugs when your app runs in different cultures.

6. What is the value of emoji.Length for the string "🚀" (a rocket emoji) in .NET?

  • A) 1
  • B) 2
  • C) 3
  • D) 4
Show answer

✅ Correct: B

Why B is correct: In .NET, strings are UTF‑16 encoded. The rocket emoji 🚀 is represented by a surrogate pair — two UTF‑16 code units (0xD83D and 0xDE80). Length returns the number of UTF‑16 code units, which is 2.

❌ Why A is incorrect: While it's one visual character (a Unicode scalar), Length counts code units, not visual characters.

❌ Why C and D are incorrect: The emoji is exactly two code units; no extra bytes for BOM or other markers.

Reinforcement: This is a common pitfall. Length does not count Unicode characters — it counts UTF‑16 code units. Use StringInfo.LengthInTextElements or EnumerateRunes() if you need to count visible characters.
